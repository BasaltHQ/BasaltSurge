## Prioritized findings

### P1: Reset does not invalidate asynchronous work — reproduced

`src/hooks/useStripeEmbeddedOnramp.ts:1752` destroys the coordinator and clears state, but does not invalidate an attempt generation. The authentication callback around line 4013 and continuation around line 4054 check mounted state, not whether they still belong to the current attempt.

Mock reproduction using the existing hook harness: defer authentication, start checkout, reset, then complete the old authentication callback. The hook repopulates `cryptoCustomerId` and calls `/api/stripe/link-auth-tokens` after reset. No payment was submitted in this reproduction. This proves stale state mutation, not a real-world duplicate charge.

Remediation: give every attempt an identity/cancellation scope; invalidate it on reset, customer/receipt changes and unmount. Validate it after every awaited operation and inside callbacks before writes or payment work. Destroy alone is insufficient for pending application fetches and callbacks.

### P1: Pre-payment generic errors can permanently disable retries — reproduced

At `src/hooks/useStripeEmbeddedOnramp.ts:4086`, an unstructured token-exchange failure becomes an unknown policy error. At line 3789, `startOnramp` rejects even deliberate force retries when that policy has `canRestart: false`.

Mock reproduction: token exchange returns an error without a code, before any checkout call. Restore the token service and invoke deliberate retry. No new request occurs and no checkout has ever been submitted. The same conservative policy used for uncertain submitted payments has trapped an unsubmitted authentication flow.

Remediation: retain one error registry, but give it explicit operation and submission context. Allow bounded, deliberate recovery for pre-payment service failures. Preserve reservation protection for submitted payments. Do not infer these distinctions from message wording.

### P1: SDK-only payment failures have no complete recovery contract

The current incident demonstrates this operational gap. The server knows only that its checkout POST completed, and the client reports a generic error without a machine-readable decline. Repeated session retrieval provides no additional reason. Our guard prevents replacement, but we have not established a documented, safe path to recover this category automatically.

Do not resolve this by interpreting “declined” in prose, by expiring the reservation solely on a timer, or by treating all `requires_payment` sessions as safe to replace. Obtain Stripe's prescribed recovery semantics for a settled `performCheckout` rejection of this kind, including whether the same session/payment method can be retried and how to authoritatively rule out an in-flight next action. Then encode and test that contract in the central policy and server reservation layer.

### P2: Error policy still has a second terminal-code list

`src/lib/stripe-onramp-status.ts:21` defines terminal error codes separately from `src/lib/stripe-onramp-errors.ts`. Its helper at line 125 also accepts `last_error.type` as a code fallback. For example, explicit `crypto_onramp_identity_verification_failed` is terminal in the central registry but absent from this second list. Status polling and server recovery guards can therefore disagree.

Remediation: keep status transitions in the status module, but delegate error-code classification to the registry. Test each terminal registry code through both consumers, including accepted-status precedence.

### P2: Wallet registration failures are swallowed

`src/hooks/useStripeEmbeddedOnramp.ts:4567` treats every thrown registration error as possibly meaning the wallet already exists, then continues into payment collection. It does not establish that the requested wallet/network is registered. This includes transient and authorization failures.

Remediation: reuse a wallet only after an authoritative match; propagate other registration failures through the same structured policy before payment collection. Stripe's [wallet registration instructions](https://docs.stripe.com/crypto/onramp/embedded-components-integration-guide?platform=web) require registration before onramping.

## Documentation and browser checks

Stripe assigns required browser actions, including 3DS, to `performCheckout`. Its callback must return the checkout POST's client secret and may run more than once. HTTP 200 alone does not establish completed checkout. Our current callback placement follows this contract, and the route test permits sequential callbacks on the same reserved session. See [Stripe's checkout integration contract](https://docs.stripe.com/crypto/onramp/embedded-components-integration-guide?platform=web).

Source inspection has not established a modal covering 3DS. Earlier checks found permissive Stripe frame policy and a payment host retained during checkout. Unit tests cannot prove Safari iframe visibility, focus, hit testing or real bank challenge behavior. Validate these in a Stripe-supported test scenario that actually requests 3DS, including inside the merchant's embedding iframe. Do not use a plain successful sandbox card as proof.

The documented API examples include `crypto_onramp_beta=v2`; current routes generally omit that suffix. Successful live calls make this a version/feature-gate question for Stripe, not proof of the decline's cause. The documents also allow risk-driven identity challenges below tier limits. Review the fully-verified EU short circuit at hook line 1954 against that behavior; do not assume every new verification request is contradictory. [Stripe integration reference](https://docs.stripe.com/crypto/onramp/embedded-components-integration-guide?platform=web).

First fix and regression-test the concrete lifecycle/recovery defects; a wholesale rewrite during an unresolved live incident would make attribution harder.

## Follow-up: R-770279

A subsequent read-only investigation confirmed session `cos_1UGpRVAdHGlTKO2bN6M3mLzo` and checkout request `req_VB4ViQDInVLvUr`. The checkout journal records HTTP 200 with no structured error. The SDK subsequently reports `generic_onramp_error` with “Your card was declined. Please try a different card.” A fresh Stripe GET still returns `requires_payment`, null payment method, null last error and null transaction ID.

This attempt's log includes `checkoutCallbackInvoked: true` and `checkoutResponseReceived: true`. The referenced public application bundle was retrieved successfully and contains those diagnostic fields. Unlike the earlier incident, this confirms that this client includes the newer checkout instrumentation. The bundle's `[STRIPE HEADLESS] Error:` location is an application error-reporting callback, not evidence of the internal failure location.

Inspection of the [public Stripe onramp SDK](https://js.stripe.com/crypto-onramp/v1/crypto-onramp.js) at investigation time shows `performCheckout` retrieving the PaymentIntent, examining its status, and conditionally invoking `handleNextAction`. If that call returns an error, the SDK wraps its message in `GENERIC_ONRAMP_ERROR` while reporting the original `error_code` and `stage: handle_next_action` to Stripe's own telemetry. This is one possible source of the observed generic error, not proof that this particular attempt reached that branch. The exact historical SDK bytes served to the customer's browser were not captured.

Request Stripe's internal next-action telemetry and 3DS result for `req_VB4ViQDInVLvUr`. A 3DS flow can be frictionless and need no visible challenge; failure or rejection alone does not prove a modal obstruction. [Stripe 3DS flow documentation](https://docs.stripe.com/payments/3d-secure/authentication-flow).

The log sanitizer redacts the serialized `returnedClientSecret` boolean because its name ends in a credential pattern. This follow-up changes only the diagnostic key to `checkoutResponseUsable`, leaving the actual secret redaction and checkout behavior unchanged. A regression test verifies both boolean values survive the full object/string sanitization path and actual secrets remain redacted. This local diagnostic change is not deployed.
