**Platform analytics: enterprise interface audit and implementation plan**

Prepared September 6, 2026. Scope: the supplied heatmap screenshot, the workspace implementation of PlatformAnalyticsPanel, its analytics API, shared metric/failure/fee helpers, PDF/XLSX reports, treasury data and chart, and relevant authorization/admin mounting code. This document records the pre-implementation audit; source line references describe that snapshot. The subsequent changes and validation are recorded in [the implementation status](./platform-analytics-implementation-2026-09-06.md).

The user subsequently authorized the non-authentication work and explicitly deferred authentication. The authentication recommendations below remain planning material; no login, cookie, wallet authentication, authorization policy or authentication gate changes were made in this implementation.

The recommendation is to retain the platform's unusually detailed investigation capabilities while rebuilding the page around a consistent query, explicit metric definitions, an accessible transaction investigation surface, and distinct reporting, reliability, and treasury workflows. Data consistency and access enforcement should precede the visual redesign.

**1. Evidence and limits**

- The screenshot verifies the supplied failure matrix appearance. Other visual and interaction findings are source inspections, not observations from an authenticated production session. No authenticated analytics browser tab or local development server was available in the inspected environment.
- All 13 existing tests in platform-analytics-metrics.test.ts, platform-analytics-failures.test.ts and platform-analytics-fees.test.ts passed. These cover helper behavior, not page accessibility, API authentication, query/export parity or production performance.
- Browser policy blocked opening the local proposal preview. The proposal received static inspection; rendered layout, theme and keyboard checks remain acceptance work.
- No production records, customer data, operational actions, settlements or deployment settings were changed or tested. External gateway protections, deployment configuration and actual dataset scale remain unverified.
- Existing unrelated workspace changes were left intact. Source references refer to this checkout on the audit date.

**2. What is already valuable**

The page has meaningful functionality to preserve: three clearly explained completion definitions, server aggregates independent of the receipt display limit, identity-based receipt deduplication, explicit KYC lifecycle cohorts, detailed payment and split evidence, multiple investigation sections, complete-result report collection, cancellation/progress, and separate treasury exploration. The shared failure helper deduplicates repeated signals within a receipt, and the batch loader already guards against duplicate and prematurely exhausted batches. These are good foundations.

The problem is that those capabilities do not consistently share the same population, identities, time boundaries, failure taxonomy, or interaction components. An enterprise interface must make a number reproducible all the way from a summary to its underlying records and export.

Authentication clarification following review of the existing login: reuse **cb_auth_token**, the signed HttpOnly cookie already issued by [the signature login route](<U:/BasaltSurge/portalpay-official/src/app/api/auth/login/route.ts:54>). No separate analytics sign-in is required. The existing [getAuthenticatedWallet(req)](<U:/BasaltSurge/portalpay-official/src/lib/auth.ts:72>) reads and verifies the token; the analytics API should derive its identity from verified cookie claims, then resolve platform access on the server through [resolveAdminRole](<U:/BasaltSurge/portalpay-official/src/lib/authz-server.ts:46>) and the applicable permission policy. Never use the plain cb_wallet cookie or x-wallet header as identity proof. Missing/invalid authentication should return 401, and a valid identity lacking platform access should return 403.

There is an additional issuance issue within A01's authentication scope: [auto-login](<U:/BasaltSurge/portalpay-official/src/app/api/auth/auto-login/route.ts:45>) accepts a submitted wallet, checks request origin and address syntax, and issues the same cookie without verifying a wallet signature or OAuth/session proof in that route. Repair issuance to verify a trusted identity bound to the wallet, or restrict privileged authentication to verified signature-login tokens until an equivalent embedded-wallet proof is implemented. Missing signing configuration must fail closed. Test this issuance boundary, along with invalid/expired cookies, forged wallet headers, non-platform users and existing administrator access. No production exploit was attempted; upstream protections remain unverified.

Access recommendations follow the principle of verifying permissions on every request in the [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html). Interaction acceptance should target [WCAG 2.2](https://www.w3.org/TR/WCAG22/), including keyboard operation, contrast, focus visibility, status messages, reflow and target sizing.

**4. Proposed information architecture**

Keep Platform Analytics within the admin shell, with five workspaces: **Overview, Conversion & Brands, Failures, Transactions, Treasury**. A persistent **Reports** action exposes all four report types and both formats. Each workspace retains the same applicable query. Treasury explicitly displays its separate wallet/network/history/price scope.

The persistent header contains page title, source freshness and refresh, then a query bar with date range, named timezone, brand, status, KYC and applied search. Compact controls can reveal advanced filters without hiding the active selection chips. Calculation basis remains visible beside metrics it affects. Report output states the query, metric basis and data version. Search edits should not silently change metric populations before they are applied.

Overview should answer: how much activity occurred, how much completed, what volume/fees resulted, and what changed? Use compact completion, paid GMV, platform-fee and AOV summaries with counts/coverage; a primary trend; a compact outcome distribution; funding/KYC details; and direct paths into an investigation. Each comparison names its actual window. Do not put every configuration switch and every diagnostic panel above the ledger.

Conversion & Brands houses rate/volume trends, brand comparisons, funding and KYC cohorts. Failures houses reason frequency, unique co-occurring pairs and linked evidence. Transactions is a dedicated searchable ledger with an investigation drawer. Treasury contains balance/token history and explicitly labeled scenario exploration. The current rollercoaster remains available as an optional presentation action.

Use one consistent visual system: quieter opaque surfaces, clear section hierarchy, readable operational text, aligned numeric columns, limited accent colors, visible selected states and unambiguous buttons. Rose signals errors; brand colors identify brands; neither replaces written labels. Support comfortable and compact table density. Keep important counts and actions readable at narrow widths and 200% zoom.

**6. Failure visualization recommendation**

Replace the default square with **ranked error frequency bars plus unique co-occurring pair rows**. Keep a compact triangular matrix as a secondary analytical view. This separates two different questions: which errors affect the most records, and which errors occur together?

The screenshot has five marginal counts: 7, 6, 5, 4, 4. It has only two nonzero unordered pairs: E1 with E2 (1), and E2 with E5 (1). The other eight distinct pairs are zero. The current 25 cells therefore contain 15 distinct quantities: five marginal totals plus ten unordered pairs. Ten cells duplicate the other half. Only seven nonzero quantities need prominence in the default presentation.

Under the current helper's counting contract, the five displayed reasons cover **24 of the 26 affected receipts**: their marginal totals sum to 26, less the two disjoint overlaps. A triple overlap would require another nonzero pair, which this screenshot does not contain. This implies two affected receipts have only reasons outside the top five. This is an inference from the screenshot and helper, not a separate production query.

The new display should therefore include the affected population, counting unit and top-N coverage; the top-five list must not imply it exhausts the 26. Actual implementation should calculate coverage from receipt reason sets, not use pair subtraction in the general case.

Interaction specification:

1. Each ranked reason shows a stable code, readable reason name, affected count and optionally percent of the explicitly named affected population. Counts are non-exclusive. Keep full raw messages in detail.
2. Each pair appears once, sorted by affected count, with both readable labels. Label it as occurring in the same receipt. It is inclusive: other reasons may also exist on that receipt. Never imply order, correlation strength or cause.
3. Zero pairs remain inspectable through an All pairs disclosure or triangular matrix; the full reason list remains searchable/pageable. This preserves existing zero-cell information and makes more than five reasons accessible.
4. Selecting a reason or pair creates an explicit filter chip and opens/pins matching receipt evidence from the complete server population. Clicking again or Clear removes it. Reset the ledger cursor on selection.
5. Show result count, complete/partial state and the selected reasons above evidence. The report must apply exactly that predicate and name it in its scope metadata.
6. Keep frequency bars and pair intensities on separate, labeled scales. Diagonal frequency must not wash out the co-occurrence signal.
7. Provide keyboard buttons, touch targets, accessible data text, stable focus and announcements after selection. Avoid hover-only discovery.
8. Handle no errors, one reason, no overlapping reasons, dense overlap, very long labels, recovered payments, missing evidence and large reason catalogs explicitly.

The included proposal uses E1–E5 only because the screenshot does not reveal their real names. It is presentation-only and does not query actual receipts.

A triangular matrix is the lowest-risk incremental change, but it retains space for many zero pairs and still makes users scan a grid. A network/chord graphic would add layout and edge-reading effort to two relationships. Exact-combination/UpSet analysis can be useful later when three-or-more-error combinations matter, but it requires receipt-level reason sets; a pairwise matrix cannot generally reconstruct exclusive combinations. Do not repurpose the current matrix as a sequence or funnel.

**7. Technical implementation plan**

Create one typed analytics query contract containing resolved date bounds, timezone, canonical brand, outcome/status, KYC dimension, committed search scope/value, reason selection and metric basis. Keep pagination/sort and presentation preferences separate. Serialize navigable state to a URL; persist user display preferences independently. Validate query values and permission scope on the server.

Return query metadata with resolved bounds, applied scope, source watermark, generated time, completeness and definition version. Metric values carry unit, numerator/denominator where relevant, counting basis and provenance. Missing, zero, unknown, estimated and stale values are distinct states.

Extract normalization and calculation functions shared by aggregation, ledger and reporting. Normalize outcome, brand, funding, KYC, receipt/intent identity, fee source and error IDs. Aggregate over those canonical dimensions. Define cohort attribution before caching daily rollups.

Split data fetching into summary/series, failure aggregates, cursor-paginated receipt rows, per-receipt evidence, treasury and reports. Fetch detailed/raw telemetry only when opened and authorized. Use bounded requests, cancellation and query-keyed caching; do not run data fetching inside render. Preserve last successful results with an explicit stale state. Report jobs should use a verifiable population and consistent snapshot contract.

Extract reusable QueryBar, MetricSummary, TrendExplorer, BrandComparison, FailureExplorer, ReceiptLedger, ReceiptInvestigation, ReportCenter and TreasuryExplorer components. Reuse existing accessible primitives and chart infrastructure where they meet the needs; no chart-library migration is inherently required. Centralize formatting, link construction, loading/empty/error states and interaction semantics.

**9. Verification checklist for implementation**

- Query parity: the same scope yields matching full-result aggregates, reason/pair evidence and report records independent of page size or fetch limit.
- Identity: conflicting session IDs remain separate; immutable revisions across midnight stay one intent under the chosen cohort rule; bridge records linking existing clusters are explicitly tested.
- Outcomes: pending, paid, failed, rejected, cancelled/expired, recovered and evidence-only signals are handled by documented predicates; accepted payment and settlement are not conflated.
- KYC/brand/funding: conflicting legacy fields, unknown values, inferred brands and nested sessions reconcile across filters, profiles, rows and exports.
- Time: Pacific/local/UTC where supported, DST transitions, custom ranges, midnight during batching and equivalent elapsed comparison windows.
- Failure sets: repeated error telemetry once per receipt, paid receipt with historical errors, history/KYC-only error, triple overlap, zero pair, top-N omitted coverage and no-detail fallback. Inclusive pair counts are never summed as unique population totals.
- Paging: selecting a rare error on page 2 returns the matching result; changed queries reset the cursor; tied timestamps, inserted/updated/deleted/backfilled records obey the documented consistency contract.
- Reports: all four types in both formats preserve scope, identity/metric basis, reason selection, date/timezone and snapshot/version metadata; long data and interrupted jobs behave predictably.
- Investigations: all eight possible sections, conditional crypto view, full fee trace, logs/customer history/limits, copy/explorer links, authorized reconcile/telemetry and multi-record expansion work on desktop and mobile.
- Accessibility: keyboard-only end-to-end workflow, screen-reader names/states, focus containment/return, visible unobscured focus, non-color encodings, contrast, reflow, reduced motion and touch targets. Test narrow mobile widths, tablet, desktop, 200% zoom and long localized labels.
- Reliability: initial empty/loading, stale after refresh failure, partial batch, missing/truncated logs, permission denied, offline, expired authentication and export failures remain distinguishable and recoverable.
- Scale: use realistic receipt and telemetry sizes at 10k, 100k and the expected upper deployment range. Agree API latency, time-to-first-useful-content, browser memory, DOM-row and report-duration budgets with the actual service capacity, then measure them. No performance numbers have been asserted by this audit.

The release criterion is a traceable and accessible operational interface: every important metric has a definition and source, every selected aggregate leads to the same underlying records, and every existing investigation/reporting capability remains available.
