# Receipt attachment timestamp mismatch

Reported receipt: `ec7bb2e5fbfd49e994eb7b603d0adcea`. The client recorded `stripe_session_receipt_attachment_failed` twice, HTTP 503. Both session creation routes emit this error only after Stripe session creation succeeds and the receipt-linking operation throws. The browser message intentionally omits the underlying database exception; the matching server log is required to confirm which exception affected this receipt.

A reproducible defect exists in the MongoDB adapter: create/replace stores `lastUpdatedAt` as a BSON Date, and reads expose it as epoch milliseconds. The recently added conditional receipt writes compare that numeric value directly against the stored Date. MongoDB equality distinguishes those types, so the patch returns no match and throws 412 even if nothing changed. Retrying the same comparison cannot repair it. Earlier patches also wrote numeric timestamps, leaving mixed storage formats.

The adapter now matches either storage representation of exactly the observed instant, retaining every other concurrency condition. Timestamp sets use the same mapping as create/replace. Regression tests exercise both formats through read/patch and verify that changed timestamps and session identities still block stale updates. Tests failed before the fix and passed afterward. Validation: 64 focused tests passed, and checkout recovery dependency typechecking reported zero diagnostics. No live receipt was modified and no new payment session was requested.

The accompanying `Authentication required` error has a separate, identified origin. Inspection of the public deployed chunks mapped the stack to Thirdweb Bridge `/v1/tokens`, `getToken` caching, and `useTokenQuery`. The latter calls `Promise.reject(err)` without returning it from its catch callback, explaining why a token API rejection becomes an unhandled promise. This is not evidence of an expired Stripe Link or PortalPay login. The installed Thirdweb source contains the same catch behavior. The failed Bridge request's status, error code and client-ID configuration are still needed to identify the authentication rejection's cause; no third-party SDK or authentication configuration was changed.

Follow-up: all four portal fallback widget mounts now wait for checkout configuration and defer to the direct Stripe flow while its autostart is pending. An active V2/headless flow continues rendering its own interface; configured alternatives and the existing opt-out remain available. Attachment failures now include a stable code, stage, and Stripe request ID when supplied by Stripe. Server logs correlate the receipt and created session with the underlying exception; the client label explicitly states that session creation succeeded but attachment failed. The 53 affected database, creation-route and embedded checkout tests passed, as did checkout TypeScript checking. These changes remain local until deployed.
